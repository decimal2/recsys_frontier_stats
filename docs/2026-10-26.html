TGR-EvoDAG：面向腾讯生成式推荐的基于 DAG 的多智能体代码进化框架

TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent ↗

全文机构行（模型提取） · 论文更新于 2026-10-23（UTC）

有完整 GR pipeline 自动进化、阶段成本规划和腾讯线上 A/B 结果，适合关注 LLM agent 做推荐算法迭代、生成式推荐落地的工程师；但方法偏框架与 agent 编排，单模型细节较少。

研究问题

论文研究如何用 LLM agent 自动进化生成式推荐（GR）的完整代码管线。现有通用代码进化搜索强但缺推荐领域反馈，推荐专用进化有诊断反馈却多为线性/贪心搜索；直接拼接在 tokenization→预训练→对齐的级联 GR 上会因阶段重训成本不对称和上游改动延迟收益而失效。

核心方法

TGR-EvoDAG 把代码进化历史组织成 Code DAG，用 Explore/Mutate/Merge 三种算子保留多分支并合并互补创新；每轮由 Operator Selector、Architect-Critic、Coder-Reviewer、Distiller、Pruner 等 LLM agent 通过结构化记录协作。关键改动有两点：节点记录编辑触及的阶段与实际 GPU-hour，Operator Selector 据此做 stage-aware 成本规划；Pruner 对因上游改动导致暂时回退的节点打 [Needs-Downstream-Adaptation] 标签，冻结上游并调度下游再适配，而不是直接剪枝。

实验结果

  • Table 1 报告 TGR-EvoDAG 的 test Hit@10=0.0869、Hit@20=0.1389、NDCG@10=0.0478、NDCG@20=0.0609。
  • 相对最强非进化基线 APAO，离线指标最高提升 37.4%，Agent4Rec 模拟用户满意度提升 19.7%。
  • 在腾讯大规模商业媒体平台的工业部署离线评估中，进化后的 GR 相对提升 Hit@1 12.16%。
  • 线上 CTR 提升 0.40%，原文称统计显著；摘要未说明该 0.40% 是相对还是绝对口径。

工程 insight 分析推断

  • 级联 GR 的搜索预算应按阶段重训成本调度，而不是按迭代次数均分；先让较便宜的下游成熟，再择机重训 tokenizer，可避免预算被上游吞掉。适用于 tokenizer→预训练→对齐这类多阶段训练管线。
  • 上游改动短期掉点不一定应剪枝；保留节点并强制下游 co-adaptation 可能释放延迟收益，前提是有诊断信号判断这是兼容性问题而非不可恢复崩溃。
  • 通用搜索加领域诊断还不等于最优，DAG 多分支合并与成本规划是额外增益来源；工业团队若已有诊断工具，应优先补搜索拓扑和预算路由。

局限与阅读提醒

  • 分析者判断：进化实验主战场是 Amazon Office 这一较小数据集，统一预算 24 GPU-hour；更大数据、更长搜索预算下是否仍优于手工管线未知。
  • 分析者判断：线上仅在腾讯媒体平台以新增召回通道做 A/B，系统 CTR +0.40% 的绝对/相对口径摘要未明示，长期生态与多业务泛化未验证。

04今日专题

级联生成式推荐自动进化的关键：搜索拓扑与重训成本协同

从该样本看，TGR-EvoDAG 的关键特点是：让 LLM 参与代码进化，并把进化历史组织成 Code DAG，使 Explore、Mutate、Merge 三种算子能保留多分支并合并互补改动。论文中的取舍在于：更丰富的搜索拓扑能提高发现延迟收益的机会，但在级联管线中，tokenizer 等上游编辑会触发全管线重训，成本远高于下游架构调整。因此，论文用 GPU-hour 和编辑触及的阶段做预算路由，并用上游冻结、下游再适配标签替代立即剪枝。工程上可借鉴（推断）：先建立阶段级成本账本，再分配探索预算；对短期回退但可诊断的节点，保留并让下游协同适配，避免因贪心丢弃；同时监控语义 ID 冲突等分布信号，避免把兼容性问题误判为无效创新。该思路适合 tokenizer、预训练、对齐构成的多阶段系统，但前提是流水线可模块化重训、指标可归因。
