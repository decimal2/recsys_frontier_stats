  2. TGR-EvoDAG：让多个代码实验分支共同改进生成式推荐把自动改代码的过程组织成可分叉、可合并的实验图，并按重训成本分配预算，保留需要后续适配的暂时退步方案。
  3. CRM：把期望观看时长变成召回模型的输入给用户塔一个期望观看时长，让同一套召回模型在不同目标之间调整，同时保留可预计算的商品索引。
  4. 推荐模型训练提效：先找出 GPU 没有推进新数据的时间把排队、启动、编译、保存和故障恢复纳入训练效率，定位每一段浪费时间，再按真实关键路径优化。

Alibaba阅读优先级 ★★★★★

UniSGR-V2：生成商品编号时，先预测商品属性

UniSGR-V2: Stepwise Target-Side Feature Anticipation and Crossing for Generative Recommendation ↗

作者署名机构包含Alibaba。 · 论文更新于 2026-10-12（UTC）

适合做生成式召回的团队：论文解释了为什么商品编号生成器难以利用排序模型常用的商品属性，并给出有线上验证的补充方法。

研究问题

传统排序模型已经拿到候选商品，能查到品牌、店铺、类目等属性，再判断用户是否会购买。生成式推荐却是逐段生成商品的语义编号（SID），编号尚未生成完，就无法查到具体商品的属性。等确定商品后再补特征，已经来不及纠正前面选错的编号。论文要解决的是：如何在生成过程中提前利用这些缺失的信息，并让同一份信息继续服务排序。

核心方法

作者提出 TacGR。模型先读取用户行为；生成第一段编号前，用历史点击商品的属性均值提供先验。生成后续编号前，再根据用户历史和已生成的编号，预测一个连续属性向量，相当于先猜目标商品可能属于什么类别、品牌和店铺。向量经注意力与历史、编号前缀交互后，帮助预测下一段编号，最终也送入点击、加购、购买预测头。

训练还要防止“预测值和可学习标签一起变成常量”：因此增加一个使用真实商品属性预测业务目标的辅助塔，让属性向量保持区分商品的能力。注意力掩码则隔离预测噪声，属性信息通过专用输出分支影响生成，而不任意流入编号隐藏状态。线上移除辅助塔，并将属性预测与编号处理合并执行，控制新增成本。

实验结果

  • 在 Lazada 的 24.2 亿条样本上，点击目标的前100候选命中率由 UniSGR 的 0.3031 提高到 0.3148；四项点击/支付召回指标均提升，最大相对增幅为3.86%。
  • 同一离线实验中，点击 AUC 从0.6750提高到0.6786，支付 AUC 从0.8438提高到0.8505；分别相对提高约0.53%和0.79%。AUC衡量正负样本的区分能力，这些数值不是百分点增幅。
  • Lazada 首页“猜你喜欢”进行了40天、10%实验流量的 A/B 测试，只替换原生成式召回模型。商品页浏览量、订单量、成交额分别相对提高0.79%、5.55%、3.09%。

工程 insight 分析推断

  • 如果生成式召回已经拥有可靠的商品属性日志，可以先验证“预测属性是否有用”，再增加复杂生成步骤。将多种属性压成一个向量，尤其适合属性多、延迟预算紧的场景；收益仍取决于预测向量是否保留了真实商品差异。
  • 训练时可读取真实目标属性，线上则只能使用预测属性，两个路径要分别验证。辅助任务既要约束标签表示，也要检查噪声如何影响后续生成，不能只看属性回归误差下降。

局限与阅读提醒

  • 品牌属性比类目更难预测。数据中前5%的品牌占83.1%的样本；作者认为这种集中分布增加了品牌区分难度，品牌整体的重建质量仍低于其他属性。
  • 线上证据来自 Lazada 首页特定召回通道。论文中的注意力隔离分析依赖训练时使用真实编号前缀，不能据此认为实际生成中的编号错误也已完全消除。

TGR-EvoDAG：让多个代码实验分支共同改进生成式推荐

TGR-EvoDAG: A DAG-based Multi-Agent Code Evolution Framework for Generative Recommendation on Tencent ↗

作者署名机构包含Tencent。 · 论文更新于 2026-10-23（UTC）

适合建设自动实验平台的团队：重点是如何安排实验、保留失败经验和计算真实成本，而不只是让模型不断提出新点子。

研究问题

生成式推荐常包含商品编码、生成模型预训练和偏好对齐三个阶段。改动商品编码可能需要整条链重新训练，改动对齐损失却便宜得多；而新的编码方式刚接到旧下游模型时，指标还可能暂时变差。只按迭代次数分预算、只保留眼前最优方案的自动调优流程，容易花光算力，或者错删需要继续适配的好方案。

核心方法

系统把每次实验保存为一个节点，记录代码、父实验、假设、验证结果和实际 GPU 小时数。Agent 可以从已有节点探索新方向、做小幅修改，或合并不同分支已经验证的改进。设计、代码审查、实验诊断和经验整理分别由不同角色完成。

调度器按修改涉及的训练阶段估算成本，并用实际消耗扣减预算。若诊断认为指标下降来自上游改动与下游不匹配，系统保留分支，安排冻结上游、继续调整下游；只有协议违规、代码不可执行等不可恢复问题才直接剪枝。这样既能积累便宜的局部收益，也能为较贵的商品编码创新留下预算。

实验结果

  • 在 Amazon Office 数据、统一24 GPU小时搜索预算下，最终模型的前10候选命中率为0.0869，APAO基线为0.0697；NDCG@10由0.0348提高到0.0478，后者相对提升37.4%。NDCG同时考虑目标是否命中及排名靠前程度。
  • 同一实验中的模拟用户满意度相对 APAO 提高19.7%；这是 Agent4Rec 模拟环境结果，不能当作真人满意度提升。
  • 迁移到腾讯商业媒体数据后，相对 APAO 的离线前1命中率提高12.16%。另在14天、5%线上流量的实验中，作为新增召回通道带来整体点击率提高0.40%；论文正文未明确给出该增幅的绝对/相对换算。

工程 insight 分析推断

  • 自动实验预算应按实际训练成本管理。修改商品编码和只调整损失函数的成本差别很大，记录阶段依赖与可复用产物，比给每种想法相同次数更有意义。
  • 暂时掉点的分支值得保留，但需要可检查的理由，例如编码冲突、尺度不匹配或下游未适配。只有总分下降而没有诊断信息时，持续投入同样可能浪费预算。

局限与阅读提醒

  • 主要自动搜索在较小的 Amazon Office 数据集上完成，24 GPU小时并不包含同等意义的模型 API 成本；大规模业务上的搜索成本还需单独核算。
  • 线上模型作为新增召回通道加入现有级联系统，不能将其点击率收益解读为整套人工推荐研发已经被自动替代。

CRM：把期望观看时长变成召回模型的输入

CRM: Retrieval Model with Controllable Condition ↗

作者署名机构包含Kuaishou。 · 论文更新于 2026-10-09（UTC）

适合已有双塔召回的短视频团队：可控目标只放到用户侧，便于在保留近邻索引的情况下试验目标变化。

研究问题

双塔召回先把用户和视频分别编码，再通过向量近邻搜索找候选。它很高效，却难以直接表达“这次希望用户看得更久”：观看时长同时取决于用户与具体视频，而生成用户向量时还不知道会选到哪个视频。如果为每种目标训练一条召回通道，维护成本会持续上升。CRM研究能否把目标作为模型输入，让同一模型按请求调整。

核心方法

训练时，CRM把实际观看时长作为条件，与用户特征一起输入用户塔，让模型学习“在这种观看结果下，用户会看哪条视频”。视频塔不接收这个条件，所以视频向量仍可离线计算，线上继续使用近似最近邻搜索。

线上将真实未来时长替换为期望值。生产使用的 Transformer 版本在视频序列中交替加入剩余累计观看时长条件；每次请求从最近32次观看的平均时长、最大时长中选择目标。平均条件偏向稳定的播放与互动，最大条件更鼓励长观看。系统按可调概率混合两者，通过线上实验寻找业务平衡，而不是固定让所有请求追求最大时长。

实验结果

  • 快手主端和极速版的线上 A/B 中，视频观看时长分别提高0.372%和0.457%；对应的应用总使用时长分别提高0.175%和0.196%。这些是各自实验组相对线上对照组的变化。
  • 论文对多种召回方法的比较中，CRM 的单次平均观看时长为42秒，KuaiFormer为36秒。该比较衡量召回流量的观看表现，不能与整套系统的 A/B 增幅直接相除。
  • 极速版实验中，视频播放量提高0.324%，关注量提高0.828%，说明目标混合策略并非只以牺牲互动换取观看时长。

工程 insight 分析推断

  • 改变用户侧条件可以复用同一份视频向量索引，适合先在已有双塔系统中增加可控目标。前提是历史日志中的条件有足够覆盖，不能把任意夸大的期望值都当作有效控制。
  • 观看更久与看更多、互动更多可能冲突。可将平均与最大条件作为两种明确策略，用线上概率混合控制取舍，并分别监控视频长度分布和互动指标。

局限与阅读提醒

  • 当前条件来自近期平均/最大观看时长，窗口长度及混合概率仍需线上调参；论文将更丰富目标和逐请求自适应选择留作未来方向。
  • 实验集中在快手短视频系统，未证明对冷启动用户、其他内容形态或任意连续业务目标都有相同效果。

推荐模型训练提效：先找出 GPU 没有推进新数据的时间

Optimizing Effective Training Time for Large-Scale Recommendation Systems ↗

作者署名机构包含Meta。 · 论文更新于 2026-10-01（UTC）

适合训练平台和推荐基础设施团队：即使训练算子很快，频繁重启、重复编译和发布等待仍可能消耗大量 GPU 时间。

研究问题

推荐模型需要不断学习新日志，作业往往比大模型预训练短，且会频繁重启。只看每秒训练多少样本，容易遗漏启动、编译、保存检查点和故障后重复训练的成本。论文中一个作业运行151.5分钟，只有90分钟真正处理新数据。作者希望回答：这些时间具体损失在哪里，由哪个基础设施组件负责，优化后是否真的能更早释放 GPU。

核心方法

作者用有效训练时间占比（ETT%）衡量整个作业生命周期中推进新数据的时间。先把损失拆为首次启动时间、每次故障恢复时间和故障次数，再按调度、初始化、编译、有效训练、浪费训练、关停六个阶段埋点，分别对应负责团队。

优化围绕实际瓶颈展开：用形状正确的合成批次提前编译，让数据预热并行进行；复用编译缓存并减少无效调优；异步保存检查点，降低训练阻塞；训练完成后先释放 GPU，再由独立 CPU 作业生成发布模型。由于故障恢复会重复部分启动流程，同一次启动优化还可能在多次恢复中反复节省时间。

实验结果

  • 六个受控配对基准使用8至256张 GPU，每个作业运行10至12小时、注入两次故障。优化后有效训练时间占比从59%至85%提高到80%至93%，平均增加15.5个百分点。
  • 这六个基准节省的时间中，58%发生在恢复路径、23%在关停、11%在检查点、8%在首次启动。恢复占比高，是因为故障后会重复启动、编译和部分数据处理。
  • 代表性32张 H100 的冷缓存编译消融中，按顺序启用优化后，编译从2050秒降至254秒，减少87.6%。这是特定缩小模型及缓存条件下的组件实验，不是所有生产作业的统一加速比。
  • 超过500个模型的生产集群在六个月内，有效训练时间占比从约80%升至90%以上；这反映集群实际运营趋势，其中也包含模型和训练平台构成的变化。

工程 insight 分析推断

  • 先为作业从申请资源到释放资源建立时间账本，再决定优化顺序。对于频繁重启的模型，降低恢复开销可能比继续加速稳定训练阶段更值得投入。
  • 并行化优化要看关键路径。合成批次解开编译与数据预热的依赖后，两者耗时由相加变成取较大值；继续压缩较短分支，未必还能缩短总启动时间。

局限与阅读提醒

  • 每个配对配置只运行一个作业，未提供置信区间；部分技术采用累积开启实验，增益依赖开启顺序，不能把所有单项百分比相乘。
  • 六个月生产趋势不是固定模型队列的随机对照实验，受平台迁移与模型构成变化影响，不能把全部提升都归因于某一项技术。

购物对话如何记住用户偏好：检索历史、分工处理，再看整段对话

Personalization Matters: Long-Horizon Conversation Agent with User-Centric Information in Online Shopping Interactions ↗

作者署名机构包含ByteDance。 · 论文更新于 2026-10-08（UTC）

适合开发购物助手的团队：论文把“回复通顺”与“始终记得用户想要什么”分开评测，也提供了成本与效果的对照。

研究问题

购物用户常在多轮对话中逐步补充预算、风格和使用需求。助手某一轮回答合理，下一轮却可能忘记之前的限制，或者反复询问同样的问题。因此，单轮回答质量不能充分衡量个性化效果。论文研究如何将历史评论、商品资料和对话记忆结合，并在整段交互上评估偏好保持、信息综合和购物进展。

核心方法

系统先整理用户过去的商品评论，形成偏好资料；每轮再检索相关历史对话、商品和用户评论。商品检索同时使用元数据、评论和由商品图片生成的文字描述。助手分成四个顺序角色：整理上下文、检索并排序商品、解释商品与偏好的关系、组织最终回复。模型参数保持冻结，改进来自检索与工作流。

评测基于 Amazon Reviews 2023 构造327条固定查询轨迹，各变体使用同一批用户问题。评审模型读取整段对话，分别评价是否保持用户约束、能否综合早先信息、是否推进购物任务和语气是否一致。作者还对比只用文本、去掉用户评论、合并为单角色等变体，并邀请5人试用。

实验结果

  • 327条合成购物轨迹上，满分5分的自动综合评分由无检索基线的3.74提高到检索变体的4.72至4.82。完整系统与纯文本检索系统均为4.82，因此该分数不能证明图片描述带来额外提升。
  • 在相同检索信息下，四角色完整系统相对单角色系统的信息综合分数由4.78升至4.89，对话推进分数由4.19升至4.45；代价是每轮四次助手角色调用，而非一次。
  • 5名试用者给完整系统的总体平均分为4.60，无检索基线为2.20。样本很小，只能作为探索性反馈；不能据此推算线上转化或真人总体满意度。

工程 insight 分析推断

  • 如果购物助手经常忘记用户约束，先检查可检索的历史和状态摘要是否完整，再增加角色数量。本实验中，引入检索的差距明显大于单角色到四角色的差距。
  • 评估应覆盖整段对话，例如预算有没有丢失、问题是否反复询问、最终是否形成可执行建议。商品标题在回复中出现，只能证明提到了目标，不能证明推荐符合用户长期偏好。

局限与阅读提醒

  • 查询轨迹由模型根据商品与评论生成，未覆盖自然用户互动的全部变化；用户资料生成和自动评审使用相关模型，也可能引入偏好。
  • 真人研究仅5人。完整系统每轮需要多次模型调用，论文未给出真实线上购买转化收益，部署前还需检查延迟、成本与任务成功率。

小模型选工具：先拆任务，再检索，最后从少量候选中选择

Training Small Language Models for Transferable Tool Selection ↗

作者署名机构包含Meta。 · 论文更新于 2026-10-22（UTC）

与小模型承接 Agent 工作直接相关：论文具体展示如何整理教师数据、定义可计算奖励，并验证换工具库后的表现。

研究问题

当工具库有成千上万个 API，全部说明无法放入上下文。检索器能找出与文字相关的工具，却不知道完成用户请求究竟需要哪几个；复杂指令还可能同时包含订机票、找酒店等不同需求。论文关注一个可拆分的小任务：让小模型负责规划检索和选择工具，而不是承担完整的工具执行与环境交互。

核心方法

流程分三步：模型把请求拆成单项能力；检索器按每个子任务找工具，经过阈值过滤后最多保留15个；同一个模型读取候选说明，为该子任务选一个工具，再合并所有选择。每次调用独立，只读取当前必要的信息。

训练先由 Llama-4-Maverick 生成拆解与选择样本，并清除无法从用户请求推断的工具标签，避免学生学习多余工具。监督微调学会格式后，再用强化学习分别优化两种能力：规划奖励考察正确工具是否被各子任务检索到、是否排名靠前且没有多余步骤；选择奖励只在选对唯一工具时给分。拆开训练可避免错误规划同时污染选择器。

实验结果

  • 在 ToolBench G3 的2124条测试指令上，必须“所选工具集合与筛选后的标准集合完全一致”才算成功。训练后的1.7B、4B、8B模型成功率分别为37.6%、40.3%、41.5%；提示驱动的 Llama-4-Maverick 最佳协议为30.6%。这只比较该工具选择任务。
  • 8B模型从监督微调后的36.2%提高到加入强化学习后的41.5%。论文在新工具库和新检索器上直接使用同一检查点，展示了一定迁移能力，但不同数据集的成功率差别明显。
  • TaskBench 的跨域多工具任务中，不拆任务的 Search-R1 风格大模型流程比本文方法高8个百分点；作者认为新的任务知识会成为规划瓶颈。

工程 insight 分析推断

  • 蒸馏 Agent 时可以先抽出工具选择这一边界清楚的子任务，并保存请求、候选说明、正确集合与检索结果。奖励能自动计算，但标准答案必须先清理，否则模型会学会选不必要的工具。
  • 部署时要分别测规划召回和候选内选择准确率。正确工具若已被规划或检索漏掉，继续增强选择器也无法补救；换业务时应重点检查任务能否被拆成独立子步骤。

局限与阅读提醒

  • 每个子步骤被假设为独立且恰好由一个工具解决，不处理工具输出传给下一步的依赖关系，也未验证完整任务执行。
  • 结果基于离线工具集合匹配，不能直接解释为订票、写入系统等真实操作的成功率。跨域规划仍有明显失败，训练工件也未发布。

推荐与Agent提效：先画清楚信息流和成本账本

本期六篇工作可以沿着一条思路阅读：先说明模型当时知道什么，再看它作出什么决定。UniSGR-V2在商品还没确定时补上属性估计，CRM把期望观看时长变成召回条件；它们改变信息进入决策的时机。另两篇工作处理计算：TGR-EvoDAG区分修改上游与下游的重训成本，训练效率研究追踪GPU没有推进新数据的时间。Agent工作进一步提醒我们，拆解和分工本身也需要评测。工程上可以先选一个明确瓶颈，建立基线和中间指标，再逐步增加预测分支、循环或角色，而不同时堆上所有模块。
