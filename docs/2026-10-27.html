面向推荐系统的有效秩缩放统一异构特征交互

Unified Heterogeneous Feature Interaction via Effective-Rank Scaling for Recommender Systems ↗

全文机构行（模型提取） · 论文更新于 2026-10-26（UTC）

方法设计与工程部署信息密度高：统一序列/特征交互、长期记忆检索、场景压缩和请求级解耦变体，且报告淘宝生产数据离线对比、缩放实验与线上 A/B；适合评估是否引入类似统一排序 backbone。

研究问题

工业推荐排序需在严格时延下同时建模异构特征交互、长期用户行为和跨场景依赖。现有架构常将序列与非序列特征分模块处理，限制双向信息交换；对全部语义 token 直接做同质 self-attention 又不适配序列/非序列信号的有效秩差异，共享表示还可能带来场景负迁移。

核心方法

HiRank 用统一 backbone 串联：主行为序列做门控 self-attention，候选 token 经共享 K/V 做 cross-attention；首层由主序列生成兴趣 query，并与候选条件 query 分别检索多组长期记忆；检索结果与语义特征 token 进行 head-wise mixing 和逐 token SwiGLU；末端用场景 query 压缩 token bank，再投影为多个 composite token 做高阶 attention。堆叠时交互输出回写主序列状态和下一层检索 query，形成双向耦合；另给出请求内共享用户侧计算的 user-item 解耦变体。

实验结果

  • 在淘宝首页/主搜离线 CVR 上，HiRank 相对各自最强基线的 AUC 绝对提升为 0.0009/0.0005，GAUC 绝对提升为 0.0186/0.0009。
  • Table 2 中 HiRank 的首页 AUC/GAUC 为 0.9163/0.7801，主搜为 0.8764/0.6787；其 dense 参数 299.04M、前向 1.530 GFLOPs/候选。
  • 消融中同时移除 token interaction 与 High-Rank Attention 造成最大降幅：AUC 降 0.0020、GAUC 降 0.0489。
  • 淘宝首页线上 A/B 相对生产基线：PV +0.45%、Orders/u +2.27%、GMV/u +2.86%、DAC +2.13%（相对变化）。

工程 insight 分析推断

  • 收益更像来自统一 backbone 中序列与特征 token 的反复双向交互，而非单纯堆参数：HiRank 默认 299.04M 参数低于多个 340M+ 基线，却在首页 GAUC 达 0.7801；工程上可优先尝试把特征交互输出回写序列状态/检索 query。
  • 场景适配用场景 query 压缩共享 token bank 再投影为 composite token，属于软共享而非完全独立场景塔；在场景共享行为强、场景标签可靠时可能降低负迁移，但场景极异质时需线上验证。
  • 长序列扩展比加宽/加深更值得优先扫：T=96 带来 +0.23 个百分点 AUC，而 width/depth 最多 +0.06 个百分点；但 GFLOPs 随序列增长，生产需结合截断、请求级共享和时延预算。

局限与阅读提醒

  • 论文未报告线上时延/吞吐的具体数值，也未给出 user-item 解耦变体的线上 A/B 结果；部署适用边界需按业务验证（分析者判断）。
  • 主搜 PCOC 未优于最佳基线：Table 2 中 HiRank 为 0.9864，Improv. 为 -0.0048，说明校准收益并不全面。

分层GTV估计：弥合容器级排序与物品级转化之间的鸿沟

Hierarchical GTV Estimation: Bridging the Gap between Container-Level Ranking and Item-Level Conversion ↗

全文机构行（模型提取） · 论文更新于 2026-10-23（UTC）

工业问题真实且给出离线+线上A/B结果，PLL分解和RCEF融合可直接借鉴到GTV/GMV/多SKU价值排序；篇幅短，适合优先读方法、消融和线上实验部分。

研究问题

直播电商和O2O广告按“容器”（直播间/门店）排序，但成交发生在容器内动态物品集上，形成排序粒度与成交粒度不一致。直接回归容器GTV面临单次成交高方差、物品级转化极稀疏和物品异构变化；把容器当“超级物品”或只用热门物品会低估高潜容器，误导竞价与商家ROI。

核心方法

HGE把容器—物品结构建成层级概率模型：HSAE对容器内动态物品集做集合编码，并在自注意力后注入用户/POI/上下文/query特征；PLL把点击后GTV拆成购买概率、购买数量和确定单价，替代直接回归高方差金额；RCEF用残差塔校正非top-K订单，再以样本级门控将物品聚合预测与通用回归塔（DIN+DCN）加权融合。

实验结果

  • 离线实验使用Meituan广告日志，数据集含712M条记录、121M用户、949K POI。
  • 离线Table 1：HGE的XAUC=0.8158、PCOC=0.9858、MAE=4.9915；相对CREAD的0.8095/0.7921/5.0818，XAUC高0.0063（0.63pp），PCOC高0.1937（19.37pp），MAE更低。
  • 离线消融：去PLL使XAUC从0.8158降至0.7873；去HSAE降至0.8031；去RCEF仅降至0.8146，但MAE由4.9915升至5.01299。
  • 线上A/B：RPS提升1.42%，95% CI为[+0.80%, +2.05%]。

工程 insight 分析推断

  • 对容器级GTV/GMV预估，先把金额拆为转化概率×条件购买概率×数量×单价，比直接回归零膨胀金额更稳；尤其适合多SKU门店、直播房间和多服务卡片。前提是能拿到物品级价格与至少部分物品级转化标签。
  • 物品级信号稀疏时，物品聚合与容器级回归应双路并存，并用样本级门控融合；工程上要监控门控权重、两路偏差和长尾容器，避免单品稀疏拖累整体。
  • HSAE在自注意力后注入用户/POI/query上下文，是先学物品间竞争再按请求调制的折中；对容器内物品集合动态变化、竞争关系强的排序场景更值得试。

局限与阅读提醒

  • 摘要写XAUC +0.63%，正文写+0.63pp；按Table 1的0.8158对0.8095应为0.0063绝对差（0.63pp），引用时不要写成相对百分比。
  • 离线仅见Meituan单一O2O广告日志，线上也只在主流量验证；跨平台、直播电商等其他容器形态的泛化未验证（分析者判断）。

LoopGR：通过循环深度实现生成式推荐的参数高效扩展

LoopGR: Parameter-Efficient Scaling for Generative Recommendation via Recurrent Depth ↗

全文机构行（模型提取） · 论文更新于 2026-10-25（UTC）

对做生成式召回/排序主干的工程师有直接参考：给出可落地的循环深度结构、两阶段蒸馏和工业离线对比；但线上 A/B 未报道，需自行验证延迟与收益。

研究问题

生成式推荐把下一物品预测为 SID 自回归生成，但真实系统受模型大小和推理成本约束。已有主干要么用深编码器建模长行为序列，要么把计算集中到目标解码，计算深度与参数量耦合，难以在有限预算下兼顾上下文表达与高效生成。论文要解决：如何在不按比例扩参的前提下，灵活分配上下文建模与目标 SID 生成的计算。

核心方法

LoopGR 由编码器、共享解码器和轻量共享上下文更新器组成：编码器先把历史 SID 序列编码为上下文记忆，随后高层解码循环与低层更新循环交替，解码器基于当前上下文预测目标 SID，更新器把新预测状态写回并细化上下文；高低层循环共享参数，以循环步数而非层数增加有效深度。训练上先用高预算 teacher 做任务监督，再用 RTSD 将低预算 student 初始化自 teacher，并对齐对应循环的预测分布 KL 与 log-prob 变化方向余弦，以压缩推理循环。

实验结果

  • 在公开离线基准的 12 个评测设置中，论文报告 LoopGR 与 LoopGR-RTSD 合计在 8 个设置取得最优。
  • 腾讯工业离线数据上，LoopGR 的 R@5=0.5691、R@100=0.7675，高于 TIGER 的 0.5465/0.7164 与 BARGE 的 0.5477/0.7496。
  • 相比代表性 encoder-decoder 基线，LoopGR 在性能更优的同时模型尺寸最多减少 52%。
  • RTSD 将 16-loop teacher 压到 8/4-loop student 时，batch=1 推理延迟从 211.08 ms 降到 104.01/49.82 ms；这是离线延迟测量，非线上 A/B。

工程 insight 分析推断

  • 对显存/延迟受限的生成式召回，LoopGR 提供了“用循环步数换有效深度”的路径；适用条件是业务能接受串行循环延迟，并保留低层上下文更新——去掉低层循环会显著掉点。
  • RTSD 适合“离线训高预算 teacher、上线跑低预算 student”的部署范式：可在 4-loop 下把延迟压到约 49.82ms；但论文只给出公开与工业离线数据结果，线上收益与全量服务成本仍需 A/B 验证。
  • LoopGR 的模块化 Encoder-Decoder-Updater 骨架可与现有生成式推荐增强组件 plug-and-play 组合；工程上可优先替换主干，而不是重写特征链路。

局限与阅读提醒

  • 分析者判断：腾讯工业评测是离线 Recall 对比（Table 2），未提供线上 A/B、全量部署延迟或长期收益；上线前需按真实 serving 预算复测。
  • 循环深度带来串行计算，即使压缩到 4-loop，论文 batch=1 延迟仍为 49.82 ms；两阶段 teacher-student 蒸馏也增加训练流程复杂度，超大规模候选集下的成本未验证。

DuoLM：基于语言模型的快速有效个性化推荐

DuoLM: Fast and Effective Personalized Recommendation with Language Models ↗

全文机构行（模型提取） · 论文更新于 2026-10-20（UTC）

对做 LLM 重排服务化、推理加速和蒸馏的推荐工程师有直接参考价值：方法把离线物品表示、虚拟 ID、共享 prefix KV 和 CUDA Graph 串成端到端服务，并给出质量与吞吐的取舍。但实验为离线数据集与受控 benchmark，没有线上 A/B，候选集也偏简单。

研究问题

LLM 能利用物品文本、用户历史和反馈做个性化推荐，但每个请求要对大量候选做全文本推理，在线计算和传输成本高、吞吐受限。论文要同时解决两点：一是获得紧凑、可跨用户复用的物品表示，避免全文本 cross-encoder 的候选表示依赖用户上下文；二是把模型计算节省转化为端到端服务收益，减少同一用户历史在多个候选间的重复构造、传输和调度开销。

核心方法

DuoLM 用编码器 LLM 将物品文本压成一个 EOS hidden state，经 RMS 归一化与尺度校准后，作为一个连续 embedding 替代 ranker 中的物品文本 token；ranker 以“历史物品向量+反馈文本+候选向量”为输入，用最后一个 hidden state 经线性头打分，不做自回归生成。编码器、接口和 ranker 端到端联合训练，损失为推荐交叉熵加冻结全文本教师的候选分布 KL，蒸馏权重线性升到 0.5。离线导出 FP16 物品向量表，在线用虚拟 token ID 查表；在 SGLang 上实现 multi-item scoring，一次 prefill 共享历史 prefix KV，用树状 attention mask 隔离候选，并用 CUDA Graph 重放分段 prefill。

实验结果

  • 在 Amazon Books 下一物品推荐（固定 100 候选）上，DuoLM 的 NDCG@10 为 0.5586，高于全文本教师 0.5440；Video Games 为 0.5298，教师 0.5313。
  • Books 评分预测的平均 NLL 为 0.9263，接近教师 0.9233；DuoLM 的 expected-rating MAE 和 RMSE 更低，教师的 median-based MAE 和 RPS 更低。
  • 单 H100、100 候选/请求下，DuoLM 吞吐从 C=1 的约 8,870 升到 C=64 的 26,400 candidate scores/s；C=64 时 p99 为 536.90 ms，vLLM 教师为 17,093.82 ms。
  • 固定模型与请求轨迹时，MIS 相对独立打分提升 4.81–29.3×，CUDA Graph 再带来 1.06–3.54×；VID 在评分诊断中把请求大小降低 99.0%，C=8 吞吐提升 66.5%。

工程 insight 分析推断

  • 把物品内容离线压成单向量并用虚拟 ID 查表，可把在线成本从“编码+传输全文本/向量”降为“ID+反馈文本”，适合物品内容稳定、候选量大的重排/打分场景；但一旦内容或编码器更新就要重建表，且单向量可能丢失用户相关细节。
  • 多候选共享 prefix KV 的 MIS 在高并发下相对收益更大（C=64 为 29.3×，C=1 为 4.81×），CUDA Graph 则在低并发下收益更大（C=1 为 3.54×，C=64 为 1.06×）；部署时应按流量形态组合两项优化，而不是只看单点加速比。
  • 教师蒸馏主要提升 top-1 和 NDCG，但可能牺牲 HR@10；self-alignment 增加 2.29× 训练时间且 NDCG 下降。工业落地应按目标指标调 β/τ，并先验证蒸馏是否值得额外训练成本。

局限与阅读提醒

  • 离线评测只在 Amazon Books/Video Games、0.6B backbone 上进行；候选集为固定随机未交互物品，可能比强检索系统产出的候选更容易区分，且没有线上 A/B。
  • 单向量压缩可能丢失对特定用户重要的细节；物品内容或编码器参数变化后需重新生成离线表示；吞吐测量不含训练和离线编码成本，且只在 H100 受控负载下验证。

面向智能体的自适应记忆索引演化

Adaptive Memory Index Evolution for Agents ↗

全文机构行（模型提取） · 论文更新于 2026-10-26（UTC）

如果你在做召回/重排的在线状态或记忆检索，这篇值得快速读：它把“内容不变、只改访问权重”的持久层讲清楚，并给出 count 基线、候选池 headroom 与粒度边界；不是推荐系统论文，别期待 CTR 或线上 A/B。

研究问题

长期智能体持续积累记忆，但相似条目增多会让原本有用的经验“还在却取不到”。现有系统常同时改记忆内容和访问方式，缺少把持久索引更新单独隔离、并评估其对后续查询前瞻价值的框架。论文将其形式化为 Memory Index Evolution：固定存储内容，学习一个在线更新规则，使后续检索与任务效用变好。

核心方法

AMIE 把记忆索引从内容中拆出，做成宿主检索接口上的可插拔更新层：策略读取当前 query 与宿主原生有序反馈列表，一次前向输出每个候选记忆的 keep/suppress 二值掩码；用 GPT-5.6-Sol 教师掩码和类平衡 BCE 蒸馏到 Qwen3-8B 学生。被选中的记忆按 ID 累积为有界饱和的抑制状态，再以惩罚项降低其后续排序分数。更新在答案上下文封存后提交，只影响后续查询；wrapper 接入宿主评分接口，不改存储内容、不重训宿主。

实验结果

  • 离线评测覆盖 LoCoMo、GroupMem、MemBench 三个基准与 BM25、Mem0、MemoryOS、A-MEM、Memory-R2 五个宿主；Trained AMIE 在全部 15 个下游效用对比中提升，幅度 0.70–3.37 个百分点。
  • 在论文的基准评测中，检索指标在全部 10 组对比中提升。
  • 在 GroupMem MemoryOS 上，count 策略失去效用，而 trained 选择比 count 高 3.61 个百分点。
  • BM25 回放中，检索单元从单轮变粗时，count 增益从 +1.48 降至 +0.48，并继续趋近零。

工程 insight 分析推断

  • 工业检索/推荐可把物品级持久抑制状态做成轻量重排层，但先看候选池内是否有可回收 headroom：BM25 回放中最大 count 点估计出现在高占用且缺失 gold 仍在池内的子集，池外证据无法被救回；粗粒度单元还会把证据和干扰绑在一起。
  • 先上线 retrieval-frequency count 作为零调用基线，再评估语义策略；论文中 count 接近 frozen F1，rate-matched random mask 也恢复部分增益，说明增益很大程度来自累积抑制而非语义理解。若高频记忆经常有用，则需选择性策略。
  • 学习选择性的收益是减少对反复有用记忆的伤害，但会牺牲部分未见证据收益；适合候选复用高、有用证据反复出现的场景，需用曝光分层监控两类错误。

局限与阅读提醒

  • 持久状态绑定具体 memory ID，不能跨 store 迁移；跨 store 只能迁移策略，不能迁移状态（论文明确说明）。
  • 策略拟合与超参选择在 LoCoMo 上完成，GroupMem/MemBench 只验证固定策略迁移；论文明确称 LoCoMo 结果不构成独立泛化证据。

04今日专题

专题：服务预算下的效果—效率折中：共享、循环、离线化与状态化

共同线索是把昂贵计算从在线逐候选路径移走或复用。HiRank用统一backbone让序列/特征token反复交互，并以场景query压缩token bank，靠交互而非扩参；LoopGR用共享解码器与轻量更新器交替循环，再用RTSD把高预算教师轨迹蒸馏到低预算学生，适合用串行循环换深度；DuoLM把物品文本离线压成向量，在线以虚拟ID查表，并用共享历史prefix KV、树状mask和CUDA Graph服务多候选；HGE则用容器—物品分层和残差门控融合处理价值稀疏；AMIE以可插拔持久状态抑制反复干扰项，不改宿主。工程取舍：HiRank/HGE有线上A/B但未充分报告时延；LoopGR延迟数据为离线batch=1；DuoLM吞吐不含训练/离线编码且单向量有信息损失；AMIE状态不可跨store迁移。推断建议：先定端到端时延和Top-K/校准护栏，再优先试低侵入的共享KV/离线向量/插件状态；循环深度和统一主干需A/B验证，蒸馏要检查长尾与HR@10。
