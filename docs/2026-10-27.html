01当日样本观察

保留可再次读取的证据，减少过早压缩

HiRank在多层排序中保留逐条行为，并让特征交互结果影响后续历史检索；HGE把门店价值与内部商品购买过程连接起来。两篇都在修复过早聚合带来的信息损失，但需要的细节不同：前者重在行为与候选的关系，后者依赖可靠的商品价格和订单标签。

共享参数和共享计算，解决的是不同成本

LoopGR通过重复使用解码器和更新器增加计算深度，减少新增参数；DuoLM把商品编码移到离线，并让多个候选共享用户历史计算。模型更小不一定请求更快，工程比较应同时报告参数、重复计算量、并发吞吐和尾延迟。

长期记忆需要管理访问，而不仅是保存内容

AMIE给每条记忆维护跨查询的降权状态，让常见干扰少占上下文位置。它也展示了盲目压低高频记忆的副作用：一些记录正是因为持续有用才反复出现。因此，记忆策略需要同时观察找回新证据与保住旧证据两种能力。

02今日速览

  1. HiRank：让用户行为和商品特征在排序中反复交换信息保留逐条用户行为，用多轮特征交互不断调整历史检索，并按业务场景选择最终排序信息。
  2. HGE：先估计店里会买什么，再预测店铺广告的成交价值把店铺点击后的成交金额拆成购买概率、购买数量和单价，再与店铺级直接预测融合，缓解金额标签噪声。
  3. LoopGR：重复使用同一组层，让生成式推荐多算几步交替细化商品编号预测和用户历史表示，用共享参数增加计算深度，再把较长计算过程蒸馏成少量循环。
  4. DuoLM：离线压缩商品文字，线上共享历史为多个候选打分把每件商品的文本预先压成一个可复用向量，再让排序语言模型结合用户历史打分，并减少多候选请求中的重复计算。
  5. AMIE：记忆内容不变，也能通过调整访问顺序改善回答对反复出现却妨碍检索的记忆累计降权，让原本被挤出的证据进入后续查询的上下文，同时防止误伤经常有用的信息。

HiRank：让用户行为和商品特征在排序中反复交换信息

Unified Heterogeneous Feature Interaction via Effective-Rank Scaling for Recommender Systems ↗

作者署名机构包含Alibaba。 · 论文更新于 2026-10-26（UTC）

适合维护多场景排序模型的团队：论文提供了行为序列与非序列特征如何双向交互的具体设计，并有淘宝线上实验。

研究问题

排序模型既要理解用户看过什么，也要理解候选商品、用户属性和当前场景。常见做法先把行为历史压成一个向量，再与其他特征组合；一旦压缩遗漏了信息，后面的特征模块就无法再回到具体行为中寻找线索。多场景共享训练还会遇到另一个问题：首页和搜索需要的证据不同，共用同一份摘要可能掩盖这种差异。

核心方法

HiRank保留一段可逐层更新的主要行为序列，并把更长的点击、加购、购买记录作为独立记忆。每层同时从用户近期兴趣和当前候选商品两个角度读取记忆，再将读出的证据与用户、商品、请求特征交换组合。组合结果会更新下一层的序列状态和检索查询，因此后续层可以带着新线索重新读取历史。

最后，模型用场景相关的查询从共享信息中提取摘要，再将摘要投影成多个表示，继续做交互并预测购买、加购等结果。论文用“有效秩”描述这些表示是否集中在少数方向上，作为信息多样性的诊断；它并不意味着每一层都必须让该数值变大。

实验结果

  • 淘宝首页离线购买预测中，HiRank的全局 AUC 为0.9163、按用户分组的 GAUC 为0.7801；相对各指标最强基线，绝对差分别为0.0009和0.0186。GAUC更接近同一用户内部的排序区分能力。
  • 默认模型约有2.99亿稠密参数，每候选前向计算量为1.530 GFLOPs。参数少于部分对照模型并不意味着所有部署条件下都更快，论文没有给出完整线上延迟数值。
  • 淘宝首页线上 A/B 相对生产基线，每用户订单量提高2.27%、每用户成交额提高2.86%。这是排序模型在该场景的系统效果，不能与离线 AUC 的绝对差混用。

工程 insight 分析推断

  • 统一模型的关键可以是让后续层重新读取历史，而不只是把更多特征拼接到最后。若错误主要来自早期历史压缩，保留事件级状态并更新检索查询值得单独消融。
  • 多场景共享模型可以先共享证据，再按场景提取不同摘要。上线时仍要分别检查各场景的排序和概率校准，整体提升不保证每一项指标都更好。

局限与阅读提醒

  • 主搜索场景的概率校准指标并未超过最佳对照；论文对多个场景的收益并不完全一致。
  • 论文提出可在同一请求内共享用户侧计算的变体，但未报告该变体完整的线上效果与吞吐收益；工程预算需要按真实候选数量复测。

HGE：先估计店里会买什么，再预测店铺广告的成交价值

Hierarchical GTV Estimation: Bridging the Gap between Container-Level Ranking and Item-Level Conversion ↗

作者署名机构包含Meituan。 · 论文更新于 2026-10-23（UTC）

适合门店、直播间或多商品卡片等排序场景：一次曝光对应一个容器，最终购买却发生在内部商品上，建模粒度需要衔接。

研究问题

美团广告排序展示的是门店，用户成交的却可能是门店里的某个套餐。同一门店既可能售出低价单品，也可能售出高价组合，直接用单次成交金额作标签会产生很大波动。同时，具体单品购买又很稀疏，完全依赖单品模型也不稳。论文要把门店整体价值与内部商品的购买过程连接起来。

核心方法

HGE先取门店中展示频繁的前10件商品，学习商品之间的关系，再加入用户、门店、搜索词和请求上下文，判断当前用户更可能买哪些东西。随后先预测用户是否会购买这10件商品中的任意一件；在发生这类购买的条件下，再把每件商品的购买概率、预期数量和已知单价相乘并求和，得到点击后的金额估计。这样每个子任务都有更清楚的学习目标。

为处理前10件以外的订单和单品标签稀疏，模型增加残差修正，并保留一个直接预测门店金额的通用分支。轻量门控网络按样本决定两路预测的权重，让有可靠商品证据的样本充分利用细节，也让证据不足的样本有较稳的整体估计。

实验结果

  • 美团日志的离线评测中，HGE 的金额排序一致性指标 XAUC 为0.8158，CREAD为0.8095，绝对提高0.0063；RankMixer为0.8105。因此0.0063不是相对全部对照中最强 XAUC 的增幅。
  • 预测金额与实际金额的比值为0.9858，CREAD为0.7921，理想值是1。平均绝对误差也从5.0818降到4.9915，说明改善同时涉及排序和金额估计。
  • 经过 A/A 检查后的13天线上 A/B 中，每次搜索收入相对提高1.42%，95%置信区间为提高0.80%至2.05%。

工程 insight 分析推断

  • 容器级金额预测可以先检查用户真正的购买路径，再拆成可学习的概率和数量子任务。前提是商品单价、门店归属以及部分订单明细可靠，不能仅靠一个总金额标签完成同样分解。
  • 细粒度模型与整体回归可以并存。尤其是长尾门店，应该检查门控权重、前10商品覆盖率和残差大小，避免看似精细的结构被稀疏标签主导。

局限与阅读提醒

  • 离线和线上证据均来自美团广告系统，其他容器形态的商品关系、价格变化和购买路径需要重新验证。
  • 校准比值接近1只说明总体金额更一致，不保证每个门店、价格段或用户群都校准良好；主表未提供这些细分结果。

LoopGR：重复使用同一组层，让生成式推荐多算几步

LoopGR: Parameter-Efficient Scaling for Generative Recommendation via Recurrent Depth ↗

作者署名机构包含Tencent。 · 论文更新于 2026-10-25（UTC）

适合关注模型参数、显存和推理延迟取舍的生成式召回团队：它增加的是重复计算次数，而非每次都新增网络层。

研究问题

生成式推荐通常先编码用户历史，再生成目标商品的语义编号。若历史表示从此固定，后续生成无法根据正在形成的目标进一步调整关注点；若用更多独立网络层增强计算，参数和显存又会增长。LoopGR研究能否反复使用同一组模块，让历史理解与目标预测互相修正，并在上线时限制循环次数。

核心方法

编码器先把历史商品编号变成记忆。共享解码器根据当前记忆预测目标编号的隐藏表示；轻量更新器再读取这一预测状态，调整历史记忆，让下一轮解码关注更相关的信息。两者交替多次执行，参数在各轮共享，所以计算深度可以增长，而参数量不必同比增长。

为了减少线上串行计算，作者先训练循环次数较多的教师，再用教师初始化较少循环的学生。学生既学习正确商品编号，也对齐教师在对应轮次的预测分布和前后变化方向，相当于用更少的修正步骤接近教师最终判断，而不是简单提前截断原模型。

实验结果

  • Amazon 三个公开类别的12项评测中，LoopGR与蒸馏版本合计在8项取得最好结果。各类别与截断位置并非全面领先，因此应按目标业务关注的召回深度比较。
  • 腾讯工业离线数据中，前5候选召回率由 TIGER 的0.5465升至0.5691，前100候选召回率由0.7164升至0.7675；较强的 BARGE 对照分别为0.5477和0.7496。
  • 离线单请求测量中，16次循环教师耗时211.08毫秒，蒸馏为8次和4次循环后分别为104.01和49.82毫秒。这体现计算预算与质量的取舍，不是线上端到端服务延迟。

工程 insight 分析推断

  • 参数共享节省的是模型尺寸，重复循环仍消耗计算和延迟。选型时应同时画出参数量、计算量、召回质量与真实延迟曲线，不能仅因模型更小就判断服务更快。
  • 如果先训练高预算教师，再压缩成低预算学生，应检查学生是否真的学会更有效的中间修正。论文的更新器消融表明，历史表示随预测变化本身很重要，具体用哪一种更新算子则可以替换。

局限与阅读提醒

  • 工业结果是离线召回比较，没有提供线上 A/B 或全量服务收益；单请求延迟也不能代替真实并发负载下的尾延迟。
  • 教师训练与轨迹蒸馏增加了训练复杂度，而且循环越多并不始终更好。不同业务需要重新选择循环预算和质量损失容忍范围。

DuoLM：离线压缩商品文字，线上共享历史为多个候选打分

DuoLM: Fast and Effective Personalized Recommendation with Language Models ↗

作者署名机构包含Google。 · 论文更新于 2026-10-20（UTC）

适合用语言模型做候选排序、受在线成本约束的团队：论文同时处理表示压缩、请求传输与推理调度，区分各层加速来源。

研究问题

语言模型能利用商品描述和用户反馈做个性化判断，但一次请求往往要评估很多候选。如果每个候选都携带完整历史和商品文字，模型会重复编码相同信息，服务端也要反复准备输入、传输和调度。只压缩模型算力还不够，压缩后暴露出来的服务开销同样可能成为瓶颈。

核心方法

DuoLM联合训练两个模型：商品编码器把一件商品文字压成一个向量，排序模型读取历史商品向量、用户反馈文字和候选向量，为候选输出分数。训练既使用真实交互标签，也让学生匹配读取完整文字的教师对候选的偏好分布。训练完成后，商品向量可离线导出，线上只运行排序模型。

服务端收到商品编号后直接查向量表，避免发送整段文字或完整向量。一次请求内，用户历史只计算一次，多个候选共享历史的注意力缓存；候选之间彼此隔离，保持各自独立打分。最后通过预录制的 GPU 执行图减少调度开销，使模型压缩带来的省算力转化为请求吞吐收益。

实验结果

  • Amazon Books 的固定100候选下一商品排序中，DuoLM 的 NDCG@10 为0.5586，完整文本教师为0.5440；Video Games 中分别为0.5298和0.5313。压缩后的效果接近教师，但并非所有数据集都超过教师。 NDCG@10同时衡量目标能否进入前十名及排位是否靠前。
  • 单张 H100、每请求100候选、并发64请求时，完整服务链可处理约26400个候选分数/秒，请求99分位延迟为536.90毫秒。吞吐单位是候选分数，不是完整推荐请求。
  • 固定相同学生模型和请求轨迹后，共享历史的多候选打分相对独立执行，吞吐提高4.81至29.3倍；预录制 GPU 执行图进一步提高1.06至3.54倍，增益随并发条件变化。

工程 insight 分析推断

  • 商品内容稳定、每次要排序许多候选时，离线内容编码和请求内历史共享可以同时节省重复计算。商品内容或编码器变化后则要更新向量表，维护成本也应计入方案。
  • 模型压缩和服务优化需要分别做对照。低并发更可能受调度影响，高并发更依赖历史共享；用一个最高加速比概括所有流量形态，会掩盖真正瓶颈。

局限与阅读提醒

  • 质量评测集中在 Amazon Books、Video Games 与6亿参数骨干，测试候选为1个真实目标加99个随机未交互商品，没有线上 A/B。Books报告集合还包含用于学生模型选择的2000名用户，因此不能把该结果视为完全独立的测试证据；强召回系统产生的难候选也需另测。
  • 一个向量可能丢失对特定用户重要的商品细节。服务测试在单张 H100 的受控负载下进行，吞吐不包括训练与离线商品编码成本。

AMIE：记忆内容不变，也能通过调整访问顺序改善回答

Adaptive Memory Index Evolution for Agents ↗

作者署名机构包含Meituan。 · 论文更新于 2026-10-26（UTC）

适合维护 Agent 长期记忆与检索系统的团队：论文把存什么和怎样被检索到分开，并认真比较了简单计数与学习策略。

研究问题

长期 Agent 可能已经保存了正确经验，却总检索到相似但无关的旧记录。存储更多内容并不能保证关键证据能进入有限的上下文。AMIE关注另一种更新方式：不改记忆正文、不重训原检索系统，只根据过去的检索过程调整每条记忆未来的访问优先级。难点是高频出现的记录可能是干扰，也可能恰好一直有用。

核心方法

AMIE接在原系统返回候选和分数的接口后。选择器读取当前问题与原始候选列表，一次输出哪些记忆应累计降权的二值判断。被选记录按稳定编号累积计数，再转换为有上限的分数惩罚。当前回答使用更新前的状态，答案上下文确定后才提交新状态，因此一次判断只影响后续问题。

选择器由教师的保留/抑制判断训练成小型分类输出。论文也比较了不调用模型的计数方案：凡被检索到就累计降权。降低常见竞争者的分数，可能让未被选择器见过的证据上浮；但若正确证据本身反复有用，盲目计数会伤害它，这正是学习选择性的价值。

实验结果

  • 在三个记忆基准、五种宿主系统组成的15组下游任务比较中，训练后的 AMIE 均提高回答 F1 或准确率，绝对增幅为0.70至3.37个百分点；主表多数格子仅报告点估计，不能都称为统计显著。
  • 在提供检索测量的10组比较中，训练版均改善检索指标。以 LoCoMo 的 BM25 为例，证据召回由51.94%升至53.02%；不调用模型的计数版甚至达到53.41%，说明简单基线不能忽略。
  • GroupMem 的 MemoryOS 回答准确率中，原系统为35.72%，盲目计数降至34.66%，训练选择器则提高到38.27%。两者相差3.61个百分点，展示了抑制高频记忆可能带来的风险。

工程 insight 分析推断

  • 先检查缺失证据是否仍在候选池内。如果正确记录根本没有被召回，靠降权重排无法找回；应先解决原检索器的覆盖率问题，再评估访问状态更新。
  • 计数法几乎没有模型调用成本，可以作为基线，但应监控反复有用的记忆是否被压低。不要把“出现次数多”直接当作无关；状态寿命、惩罚强度和记忆粒度都需要回放实验。

局限与阅读提醒

  • 策略拟合和参数选择使用了 LoCoMo，因而它不提供独立泛化证据；跨库可迁移的是策略，绑定具体记忆编号的累计状态不能直接迁移。
  • AMIE只能重排原系统提供的候选，找不回候选池外的记忆；同一记忆的降权状态还要保留到后续查询，才可能影响答案。论文实验均为离线记忆任务，尚未证明线上长期运行会持续受益。

04今日专题

把推荐系统拆成三本账：信息、参数与在线计算

本期工作说明“更强”和“更快”需要分开解释。HiRank与HGE首先改善信息如何进入判断：保留行为细节，或将门店总金额拆成商品购买过程。LoopGR共享的是模型参数，仍会增加串行循环，因此需要蒸馏来限制推理次数；DuoLM共享的是商品表示和请求历史，主要减少在线重复工作。AMIE则改变后续请求能访问哪些既有记忆。选型时可以分别问三个问题：错误来自缺信息还是用不好信息？成本来自参数驻留还是重复计算？新策略会不会损害已经有效的候选或记忆？沿着这些问题做对照实验，比把所有改进归为一个模型升级更容易定位收益。

HiRank：让用户行为和商品特征在排序中反复交换信息 · HGE：先估计店里会买什么，再预测店铺广告的成交价值 · LoopGR：重复使用同一组层，让生成式推荐多算几步 · DuoLM：离线压缩商品文字，线上共享历史为多个候选打分 · AMIE：记忆内容不变，也能通过调整访问顺序改善回答
