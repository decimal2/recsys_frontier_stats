# 可读性写作与验收

用于新写或重写日报的单篇解读与跨论文综合。默认读者有推荐/机器学习基础，但未读原文；不能假定读者知道论文自造的模块、缩写或特定评测协议。日报应帮助读者理解和判断，详细复现配置放在阅读笔记中。用户要求深入实现时，再展开相应细节。

## 先读清楚，再决定写什么

阅读全文时先记录：实际任务、原有方案的障碍、关键改动、输入输出、主要结果及其适用范围。必要时画出内部流程，核对训练与推理各用了哪些信息。笔记可以包含公式、超参数、模块全名、逐项实验结果与证据定位；不要求把这些全部搬进正文。

每个准备写入正文的细节都应有作用：帮助解释机制、支持结论，或影响工程决策。如果一个参数只对复现有用，移到笔记；如果一个技术名词无法解释它在流程中做什么，先补读原文，不靠换成中文译名蒙混过去。

## 各字段怎样写

| 字段 | 读者需要得到什么 | 常见失误 |
|---|---|---|
| `title_zh` | 方法名加具体问题或核心改动，能据此判断相关性 | 用多个缩写拼标题；将“重建视觉特征”写成“生成目标图片” |
| `one_liner` | 主要改动与价值；有数字时保留必要条件 | 宣称“全面领先”“效果无损”，实际只在一个指标成立 |
| `recommendation_reason` | 哪类工程师值得读、重点看什么 | 只写“创新性强”“对工业落地有启发” |
| `problem` | 任务场景、原来怎么做、具体卡在哪里 | 直接列模型名或以论文贡献列表开头 |
| `method` | 输入经过哪些关键步骤成为输出，每个改动解决什么障碍 | 逐项抄模块介绍，缺少连接；只说“多阶段优化”而没有机制 |
| `key_results` | 实验支持的发现，以及比较对象、指标含义与范围 | 复制整行结果表；混用百分比与百分点、代理分数与真实收益 |
| `insights` | 有条件的工程行动及依据，明确属于推断 | 将论文未验证的方案写成已实现收益 |
| `limitations` | 会改变采用决策的边界、代价或未验证条件 | 罗列“还需更多实验”等通用提醒 |

方法通常用几段连贯文字讲清楚，复杂方法可多写，简单方法可少写，不统一卡字数。先交代总体流程，再解释决定性机制，最后说明代价。每段集中回答一个“做了什么、为什么这样做”。保留辨识方法所需的技术细节，不能简化到任何论文都能套用。

对于多阶段训练，尤其要说明监督从哪里来、更新哪个模块、哪些参数固定。对于服务系统，要区分离线预计算与每次请求的计算。论文没交代的部分不补猜，也不强行为所有论文套用训练流水线。

结果通常挑最能支撑核心判断的几条：整体效果、解释收益的关键对照、重要代价或反例。先写这条结果说明了什么，再给数值。某方案并非每项指标都更好时，明确写出主要退让项；不必罗列所有实验数字。

## 术语、数字与句子的取舍

- 必要的新术语第一次出现时解释其作用，再给名称。例如“语义编号：用一小串编号表示商品，相关商品可以共享前缀”。只写“SID（Semantic ID，语义ID）”没有解释它如何参与任务。
- 常用中文能准确表达时，直接用“查询、候选、分支、打分、排序”等词。保留方法名和必要缩写供读者查原文，但后文不必反复展开英文全称。没有英文比例或缩写数量的机械门槛。
- 一句话若同时介绍多个机制、参数和例外，就按动作与因果关系拆开。段落中先让读者知道“为什么需要这一步”，再引入实现方式。
- 公式只有在帮助理解关键机制时才进入正文；先用文字说清变量对应的对象和公式的作用。精确学习率、温度、层宽等默认留在笔记；决定容量、成本或比较公平性的参数仍应保留。
- 指标解释与结果放在一起。命中率与召回率、离线奖励与线上业务收益、总请求时延与某个算子时延必须区分；数值条件不能为了句子流畅而删除。指标存在不同定义时，按本篇协议解释。
- 可以用简短场景辅助理解，但标明是解释性例子，不冒充论文实验。不要用“评分员”“大脑”等比喻替代对输入、计算过程和输出的说明。

## 写法对照

以下是解释方式的示例，不能当作其他论文的事实或固定模板。

### 模块名要接上实际动作

不易理解：
> Path KD 后冻结 scorer，BudgetCut 用 OPD+GRPO 优化 set-dependent admission。

可理解的写法：
> 先让小模型学习大模型对后续编号的打分，再冻结这个打分器。之后只训练一个小型分支选择器，决定哪些已打分分支进入最终候选集合。它先在自己走到的选择状态上学习“加入哪个分支能提高召回”，再根据整组分支的最终召回率优化。

需要继续讨论算法差异时，再引入 Path KD、OPD 和 GRPO 的名称。不能把这段流程概括成“整个语言模型经过 SFT、OPD 和 RL”，因为更新对象不同。

### 保留结论的范围

不易判断：
> 小模型达到大模型效果，时延下降。

可理解的写法：
> 在缓存已准备好的测试请求上，小模型的“至少找到一个目标”的比例接近大模型，平均响应更快；但找回全部相关目标的比例仍较低。因此，这个结果支持一种速度与召回量的交换，不能理解为所有质量指标都持平。

实际成稿应补上原文的基线、数值和测量范围；这里省略数字仅为展示解释顺序。

### 技术细节要说明用途

不易理解：
> shared candidate slots + selective projection + fused top-k 降低 overhead。

可理解的写法：
> 系统先确定哪些编号能对应真实商品，再只为这些合法编号计算分数。过滤、打分和选优共用同一组内存槽位，减少中间结果的搬运；候选较密集时仍采用完整矩阵运算，因为零散地少算一些，在 GPU 上未必更快。

这段保留了方案为何有效以及何时不适用，而不是仅把英文术语换成中文。

## 交付前：只读正文的复述检查

完成初稿后，暂时不看原文和内部笔记，只读准备交付的正文，逐篇用普通中文回答：

1. 任务的输入和输出是什么？原方案具体遇到了什么问题？
2. 新方法改变了哪一环？输入怎样经过关键步骤变成输出？
3. 改动为什么可能有用？若涉及训练或服务，能否分清训练对象、监督来源和上线组件？
4. 实验究竟证明了什么？对比谁、测什么、在什么条件下？有没有被标题或速览掩盖的退让项？
5. 哪类场景值得尝试，采用前最需要确认哪项条件？

答案必须能从正文找到；如果需要靠记忆原文补充，说明正文仍有缺口。对理解方法或判断结果不可缺少的缺口，回到原文核实并改写相关段落。不要用增加术语表代替重写，也不要为回答问题而编造论文没有的信息。

再检查综合部分：跨论文比较的是同一环节吗？指标口径可比吗？是否解释了不同方法的适用条件，而不是把六篇摘要各抄一句？结论仅限本期样本，实践建议标为推断。

在本次日志或阅读笔记中简记读者会卡住的位置、实际修订和仍需保留的边界。简单稿件可自查，复杂或反复返工的稿件可在授权范围内独立复核；不默认要求额外模型 API 或多轮打分。检查结构、字数、缩写密度只能发现线索，不能自动判定“人类能看懂”。

最后检查实际 Markdown / HTML：长段是否分开、公式是否妨碍阅读、来源核实记录是否误入正文。排版修复不能替代内容解释，语义审阅也不能替代手机/桌面检查。
